# NebulaBindings

C ABI bindings that let the Modularity editor drive [Nebula](../Nebula) bakes.

`Nebula/` is treated as a pristine upstream checkout: nothing in it is modified,
and it is not aware this crate exists. This crate is its own Cargo workspace and
consumes Nebula purely through path dependencies, so `Nebula/Cargo.toml` never
has to list it as a member.

## Building

```bash
cargo build --release --manifest-path NebulaBindings/Cargo.toml
```

The CMake build does this for you when `cargo` is on `PATH`
(`MODULARITY_BUILD_NEBULA_BINDINGS`, ON by default) and copies the resulting
library next to the `Modularity` executable. Without a Rust toolchain the engine
still builds and runs; the Lightmapping window reports the backend as
unavailable and the Bake button stays disabled.

## How the engine uses it

The editor does **not** link this library. `src/Nebula/NebulaLightmap.cpp`
resolves `libnebula_modularity.so` / `nebula_modularity.dll` at runtime with
`dlopen` / `LoadLibrary`, checks `nb_abi_version()` against `NB_ABI_VERSION`, and
resolves every `nb_*` symbol up front. That keeps Rust entirely optional and
means a stale library is rejected rather than half-used.

Search order:

1. `$MODULARITY_NEBULA_LIB` (explicit override)
2. next to the executable, and `./lib`, `../lib`
3. `NebulaBindings/target/{release,debug}/` for developer builds

## API shape

See [`include/nebula_modularity.h`](include/nebula_modularity.h). The header is
hand-maintained and must be kept in lockstep with `src/lib.rs`; bump
`NB_ABI_VERSION` on both sides together when anything changes.

```text
nb_scene_create
  nb_scene_add_material / nb_scene_add_mesh / nb_scene_add_light / nb_scene_set_sky
nb_bake_lightmap_start   <- consumes the scene, spawns a worker thread
  nb_bake_poll           <- polled once per editor frame, never blocks
nb_bake_write_result / nb_bake_copy_preview_rgba8
nb_bake_destroy
```

All vertex data is copied on the way in, so the engine may free its buffers
immediately after `nb_scene_add_mesh` returns.

## Known limitations

- **Cancellation is "discard", not "interrupt".** `BakePass::execute` has no
  interruption point, so `nb_bake_cancel` lets the current GPU pass finish and
  then throws the result away. The editor's Cancel button says as much.
- **The sky is flat.** Nebula consumes sky lighting as an RGBE panorama; the
  editor only exposes a colour and an intensity, so a 1x1 panorama encoding that
  constant radiance is synthesised here rather than modifying Nebula.
- **Lightmap UVs are generated by Nebula.** The engine's meshes carry only a
  single UV set, so `lightmap_uvs` is passed as `None`.
- **`nebula-serialize` exposes no `BakeSerializer` impl** despite its docs, and
  its bincode chunk helper is `pub(crate)`. `nb_bake_write_result` therefore
  assembles the `LMAP` chunk itself using the public chunk primitives
  (`write_file_header` / `write_chunk` / `write_end_chunk`). The resulting file
  layout matches what an in-tree serializer would emit.
- Only the lightmap pass is wired up. Nebula's AO, probe, audio, visibility and
  nav bakers are untouched and would each need their own `nb_bake_*_start`.
